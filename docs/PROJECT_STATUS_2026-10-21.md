# DBPulse 개발 현황 및 잔여 작업 — 2026-10-21

> 코드·설계 문서와 사용자가 공유한 로컬 테스트 결과를 함께 반영한
> **시점별 스냅샷**이다. 구현됨 ≠ 모든 현장 환경에서 검증 완료.
> 이 문서에 적힌 사용자의 실측 결과는 SQL Server 로컬
> `DBPulseLab` 환경에서 얻은 결과다. 실제 외부 고객 DB의
> 안전성과 성능은 아직 검증하지 않았다.

## 개발 브랜치 및 릴리스 경계

- GitHub: `feature/monitoring-overhead-v0.13`, Draft PR #12.
  **v0.13.0-alpha는 아직 main에 병합되지 않았다.**
- 현재 실습 대상: 환경변수로 등록한 **MSSQL 1개**, API/DB 저장소는
  로컬 Docker Compose. 외부 사용자 공개 서비스가 아님.
- 운영용 외부 접근은 **인증/인가/비밀정보 보호/대상 서버
  등록/네트워크 경계** 구현 전까지 금지.

## 현재 구현된 기능 (코드 존재 + 일부 로컬 검증)

| 영역 | 구현된 범위 | 상태·한계 |
|---|---|---|
| 로컬 플랫폼 | Spring Boot REST, React/Vite, 별도 PostgreSQL 메트릭 저장소, Docker Compose | 로컬 단일 대상 |
| DMV 성능 | 5초 활성/Blocking/장시간 요청·경과시간·CPU 시간(ms) 스냅샷, 이력, ONLINE/OFFLINE 구분 | 간격보다 짧은 SQL 일부 누락 가능, QPS 아님 |
| 인시던트 | 반복 차단/장시간 요청/수집 오류 규칙 기반 OPEN/RESOLVED, PostgreSQL 저장·조회 | 추가 경보 억제/개별 정책 등 고도화 필요 |
| Blocking | 차단 관계/체인 후보 및 이력 화면 | 샘플 한계, 진짜 근본 원인 자동 확정 불가 |
| Deadlock | SQL Server system_health XEL로부터 제한적·정제된 이벤트와 피해 세션 요약/이력 | 혼합 DB/복잡한 그래프는 부분 수집 가능 |
| Wait | 실시간 요청 Wait Type·카테고리/이력 및 인시던트 시점별 연관 근거 | 서버 전체 누적 Wait Stats가 아닌 요청 샘플 |
| 장애 조사 | 시간창 안의 DMV/Blocking/Deadlock/Wait 근거 묶음, 관측/제한 구분 | 자동 RCA(근본 원인 증명) 아님 |
| Query Store | Query ID/Plan ID, 실행·평균 지연·CPU(ms)·논리 읽기, 최근/우선순위 필터, 내부 DBPulse SQL 제외 | 집계/비동기 지연·제한된 범위 |
| 튜닝 후보 | 임계값 기반 HIGH/MEDIUM/OBSERVE, 실행계획 연산자 증거, 통계×연산자 연계, 동일 쿼리 플랜 비교 | 읽기 전용 조사 보조; AI/검증된 CREATE INDEX 자동 추천 아님 |
| SQL 원문 | 클릭 시 우측 드로어에서 특정 Query ID/Plan ID 텍스트 조회 | 기본 **비활성**, 로컬 명시적 허용 필요; 개인정보 주의 |
| Query Store 오버헤드 | 내부 SQL 분리, 상태 캐시, JDBC/쿼리 비용 휴리스틱에 따른 60s↔120s 자동 완화 | v0.13-alpha, Query Store 수집만 완화; 고객 영향 인과관계 미입증 |
| CPU(%) | 선택적 SQL Server **프로세스 전체** CPU(%) 및 호스트 CPU(%) 캐시, 개요 추이 | 실험적 ring_buffer, 기본 비활성/별도 권한·설정 필요; DB별 CPU% 아님 |
| UI | Navy/Midnight Dark, Overview/Incident/Blocking/Deadlock/Wait/Query/Investigation/Targets, 요약·필터·드로어 | 실제 브라우저에서 최신 빈 선 렌더링 확인 대기 |

## 2026-10-20~21 v0.13 검증 근거

- 사용자 공유 로컬 API smoke script 정상; frontend/backend
  GitHub CI 수행. **이것만으로 고객 현장 검증 완료는 아니다.**
- A 고정 60초, B 적응 THROTTLED 120초 테스트:
  양쪽 업무 RPC 1,200건, 총 비용을 구별하기 위해 Query Store
  내부 SQL과 업무 SQL 분리. Query Store 수집 호출 감소 관측.
- XEL A/B 분석에서 요청 지연과 다른 모니터 실행이 시간상
  겹친 경우는 있었으나 **관측된 시간 겹침만으로 차단/CPU 대기
  원인이나 자동 완화의 업무 SQL 성능 효과를 확정할 수 없다.**
- v0.13 개요 UI는 서버·DB명 구분, 실제 지표만 사용,
  두 열 독립 스택, CPU 별도 오른쪽(0~100%) 축,
  0→0 구간 색상선 숨기기(이번 수정)를 구현. **최신 화면 검수 전**.
- 실측 데이터와 보안상 민감한 XE 원본은 GitHub에 업로드하지 않는다.

## 남은 개발 — 우선순위

### P0. v0.13 안정화/정식 릴리스

1. 로컬 `npm.cmd run dev` 최신 코드에서 0값 겹침 없는
   그래프, 유효 이벤트 구간 색상/hover 값, CPU 이력·누락
   간격, 두 개의 독립 열 레이아웃(옛 빨간 공백 제거) 확인.
2. Navy/Midnight Dark, 모바일 너비, Incident 클릭 시
   Investigation, Query 원문 드로어/플랜 비교, 화면 오류 회귀.
3. `docs/PHASE13_OBSERVER_COST_MEASUREMENT.md`의
   오버헤드/업무 부하 A/B 한계와 CPU 단위 유지.
4. README/아키텍처의 예전 버전·포트·기능 상태 설명
   갱신 및 최종 릴리스 노트. 검증 충족 전 PR #12 Draft 유지.

### P1. 사용자 인증 및 대상 DB 직접 등록

1. 회원가입/로그인, 계정 및 소유자별 API 접근 제한,
   CSRF/세션 또는 토큰 정책, 감사 로그.
2. **대상 서버 탭**: 연결 이름, DBMS 종류, 서버/포트,
   DB명, 제한적 조회 계정, TLS 검증 옵션 입력,
   읽기 전용 연결 테스트·권한/지원 지표 확인,
   저장/수정/해제 및 여러 DB 선택.
3. 비밀번호 보안 저장(KMS/Secret Manager),
   로그/프론트 응답에서 비밀번호 제외, 회전/폐기.
4. 서버측 SSRF 차단, 네트워크·동시 접속 한도,
   로컬/사내 방화벽 뒤 DB의 안전한 전용 에이전트/
   승인된 터널링 정책. **브라우저에서 DB로 직접 접속 금지.**
5. 모든 Collector/Repository/Controller에
   `ownerId/targetId` 검증과 데이터 격리 테스트.

### P2. 실제 DB 운영/장애 대응 제품화

1. 안전한 알림/중복 억제/확인/온콜 채널,
   경보 정책·임계값 설정 및 사고 이력 품질 개선.
2. 원인 후보 진단 근거 확장, SQL/트랜잭션·Lock/Wait
   연계 정확도와 관찰 한계 검증.
3. **복구 워크플로**: 안전한 재접속 등 낮은 위험 조치만
   조건 검증 하 자동화. `KILL`, 강제 계획/인덱스 변경,
   DB 재시작은 기본적으로 승인/감사/롤백 필수.
4. 실제 고객 SQL 보호를 위한 수집 오버헤드 예산,
   불안정/고부하 시 자동 완화, 수집 빈도·유실 관측,
   충돌/장애/성능/권한 부족 테스트 반복.

### P3. DBA 분석 및 확장

1. Query Store 기반 **선택 DB 쿼리 CPU 시간(ms/구간)**
   추이 제공. SQL Server 인스턴스 CPU(%)와 분리.
   일반 설치형 MSSQL의 정확한 DB별 CPU%는 보장 불가.
2. 안전하고 검증 가능한 인덱스/SQL 튜닝 후보 추천,
   실행계획 전후/롤백 및 A/B 검증,
   허용/오탐 경계 구체화. AI는 보조 의견만 제공.
3. PostgreSQL 등 DBMS별 어댑터와 기능별 가용 지표
   분리; Azure SQL Database는 서비스 계층 대비
   DB CPU(%) 등 별도 지표 지원 가능성 검토.

### P4. 외부 서비스 출시

- HTTPS·도메인, 배포/이중화/백업·복구, 계정별 요금·쿼터,
  보안 진단·취약점/권한/비밀정보 감사,
  최소 권한 지원표 및 고객 데이터 보존/삭제 정책,
  사용자 온보딩·운영 장애 대응·관측성 점검.
- 실제 제3자 DB 접속은 명시적 소유자 승인과 충분한
  보안 검증 이후에만 활성화.
