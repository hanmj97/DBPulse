# Phase 14 — 사용자별 대상 SQL Server 등록 구현 계획

> 개발 준비 스펙. 현재 DBPulse는 브라우저에서 외부 DB를 등록할 수
> 없고, DB 자격증명을 저장·보호할 인프라도 아직 없습니다.
> 이 문서 자체는 그 기능을 활성화하지 않습니다.

## 시작 상태와 브랜치 전략

- 출발 코드: `v0.13.0-alpha` (Draft PR #12, 로컬 단일 MSSQL 설정).
- 작업 브랜치: `feature/target-onboarding-v0.14`.
  아직 v0.13을 main에 합치지 않았으므로 이 브랜치는
  **v0.13 브랜치의 최신 커밋에서 분기한 stacked work**입니다.
  v0.13을 병합한 뒤 대상을 main으로 재조정합니다.
- 지금 동작하는 `local-mssql` 조회 API·DMV·Query Store·인시던트
  이력을 깨뜨리지 않으며, 신규 외부 DB 연결 엔드포인트는
  모든 보안 테스트 통과 전까지 외부 공개하지 않습니다.
- 회원가입/로그인이 존재하는 것처럼 UI를 표시하거나
  DB 비밀번호를 브라우저 localStorage에 저장하지 않습니다.

## 14.1 — 사용자 인증 및 소유권 경계 (첫 구현)

- Spring Security 기반 **기본 거부 정책**.
  선택한 인증 방식은 서버가 관리하는 세션 쿠키 + CSRF 보호를
  기본 후보로 합니다. 보안 구성 전에는 임의 공개 POST 금지.
- `dbpulse_users`: 자체 회원 계정, 상태, 비밀번호 해시(강력한
  적응형 KDF, 예: Argon2id/BCrypt), 생성/갱신 타임스탬프.
  비밀번호 평문/복구 가능한 문자열 저장 금지.
- `target_owners` 또는 `targets.owner_id`: DB 타깃의 소유자
  식별자와 대상 식별자 연결. 조회 API에서도 매번 인증된
  사용자와 `target_id` 소유권 검증.
- 보호 대상에 GET도 포함: 메트릭, 인시던트, SQL 원문, 플랜,
  Deadlock, Blocking, Wait, CPU, 대상 상태 모든 API.
- 테스트: 익명 401/403; A 사용자는 B 소유의 타깃 ID를
  조회/변경/삭제할 수 없음; 로그아웃 후 세션 무효;
  CSRF 거부; 세션 쿠키 HttpOnly/Secure/SameSite 설정.
- **기존 로컬 개발 모드**와 다중 사용자 모드를 구분해 점진적
  이전. 로컬 모드는 loopback에서만 허용. 보안 스위치의
  잘못된 기본값이 공개 서비스를 허용하지 않도록 합니다.

## 14.2 — DB 등록 폼(인증 후에만 사용)

`대상 서버 > 새 연결 등록`에서 입력받을 정보:

| 항목 | 저장/표시 규칙 |
|---|---|
| 연결 이름 | 사용자가 수정할 수 있는 UI 이름 |
| DBMS / 연결 방식 | MVP MSSQL; 직접 연결보다 승인된 안전한 agent/터널 우선 |
| 서버 호스트 / 포트 | 서버측 허용된 주소 및 목적지 정책 준수 |
| 데이터베이스 이름 | 연결 후 실제 `databaseName` 필드에 저장 |
| 모니터링 SQL 로그인 | 읽기 전용 최소권한 권장 |
| 비밀번호 | **암호화된 비밀 저장소**; 목록/로그에 평문/마스킹된 값도 반환하지 않음 |
| TLS / 서버 인증서 | 기본 엄격 검증. 운영 환경에서 `trustServerCertificate=true` 불허 |

작업 단위: `입력값 검증` → `보안 범위 확인` →
`비밀정보 수신` → `연결 테스트(읽기 전용)` →
`지원되는 진단 범위·필요권한 설명` → `타깃 등록`.

브라우저는 DB에 직접 접속하지 않고 **인증된 DBPulse 백엔드
API를 통해서만** 등록/테스트합니다. 연결 테스트 실패는 대상
설정 오류를 안전한 코드로 분류하며 원본 자격증명, SQL,
전체 연결 문자열, 내부 네트워크 주소를 로그에 노출하지 않습니다.

## 14.3 — 외부 연결 보안 및 수집기 설계

- SSRF: 사용자가 제공한 호스트를 그대로 접속하지 않습니다.
  허용 정책, DNS 재확인(재바인딩 대응), 포트 정책,
  DB 전용 프로토콜 및 실제 네트워크 egress 방화벽이 필요합니다.
  공용 SaaS에서 타인 사설망에 직접 접속하는 구조는 사용하지
  않으며 **사용자 소유 환경의 agent/승인된 안전한 터널**을
  우선 설계합니다.
- 비밀: KMS/Secret Manager 또는 별도 암호화된 credential
  store; 키 회전/폐기, 감사지표. API 응답에는 평문 포함 불가.
- DB 연결: 최소 읽기 권한, 연결/쿼리 타임아웃, 접속 수 제한,
  신뢰 가능한 인증서, 데이터 수정 없음, 수집 비용 예산.
- `target_id` 별 수집기/DB 풀/보안 경계 분리; 타깃
  삭제·비활성화 시 더 이상 수집하지 않고 이력 보존·삭제 정책 준수.
- PostgreSQL 데이터 테이블은 `target_id`를 공유하므로
  API 단의 소유자 체크만으로 충분하지 않습니다.
  사용자 소유권·저장소 쿼리 범위를 테스트하고 필요하면
  RLS/테넌트 인덱스 및 버전 관리형 DB 마이그레이션 적용.

## 14.4 — 실제 화면 연결

- 타깃 목록에서 **현재 사용자 소유 DB**만 표시.
- 선택한 타깃 ID에 대한 Overview / Query / Wait /
  Blocking / Incident / Deadlock / CPU의 데이터 및 상태만 출력.
- `MONITORING TARGET`: 해당 사용자가 등록한 실제
  `databaseName`과 연결 이름/수집 시각 표시.
- CPU 그래프는 등록 DB가 속한 SQL Server **인스턴스
  전체 프로세스 CPU(%)**로 유지. 이것은 DB별 CPU% 아님.
  DB별 Query Store CPU(ms/구간)는 나중에 별도 지표로 추가.

## 수용 기준(코드 단계별 게이트)

1. 백엔드 인증/세션/CSRF/익명 및 타인 데이터 차단
   자동 테스트가 통과하기 전에는 **DB 등록 POST API 열지 않기**.
2. 비밀번호가 GET/로그/브라우저 저장소에 노출되지 않는
   실패/성공 사례 테스트.
3. 허가되지 않은 DB/호스트로의 접속 시도가 네트워크 경계에서
   차단됨을 통합 시험으로 입증.
4. READ-ONLY 모니터 계정으로 DMV/Query Store 지원범위를
   감지하되 권한을 스스로 GRANT하지 않기.
5. 두 계정이 서로 다른 MSSQL DB를 등록해도 데이터·사건·SQL
   텍스트가 섞이지 않는 통합 시험.
6. 기존 로컬 `DBPulseLab` 회귀 테스트의 안전성·CI 유지.
